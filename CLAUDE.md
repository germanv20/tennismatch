# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

TennisMatch is a Flutter mobile app (Android-focused; iOS/macOS/web/windows/linux scaffolding exists but is unused) backed entirely by Firebase: Firestore (data), Firebase Auth + Google Sign-In (auth), Cloud Messaging (push notifications), Cloud Storage, App Check, and Cloud Functions (server-side triggers/cron). There is no custom backend server — `functions/index.js` is the only server-side code.

The app lets players find opponents by tennis level/city, send/accept match requests, log singles/doubles/guest match results, chat per-match, and track win/loss stats and head-to-head records.

## Common commands

Run all commands from the repo root unless noted.

```bash
# Install Dart/Flutter deps
flutter pub get

# Run the app (Android is the primary target)
flutter run

# Static analysis (uses analysis_options.yaml / flutter_lints)
flutter analyze

# Run all tests
flutter test

# Run a single test file
flutter test test/widget_test.dart

# Regenerate localization classes (lib/gen_l10n) after editing lib/l10n/*.arb
flutter gen-l10n

# Regenerate launcher icons after changing assets/icon/
flutter pub run flutter_launcher_icons

# Build a release APK
flutter build apk --release
```

Cloud Functions (in `functions/`, Node 24, deployed via Firebase CLI):

```bash
cd functions
npm install
npm run lint            # eslint (eslint-config-google)
npm run serve            # firebase emulators:start --only functions
npm run shell            # interactive functions shell
npm run deploy            # firebase deploy --only functions
npm run logs            # firebase functions:log
```

Firestore rules/indexes are deployed separately, e.g. `firebase deploy --only firestore:rules,firestore:indexes`.

Note: `test/widget_test.dart` is still the default Flutter counter-app smoke test and does not exercise this app — there is no real automated test coverage yet. Don't treat it as a template for how the app behaves.

## Git workflow

This is a solo project with no CI/PR process — commit and push directly to `main` as you work so nothing is ever sitting only in the local working tree.

- Commit at natural checkpoints (a working feature, a fixed bug, a completed refactor step) rather than batching many unrelated changes into one commit. Don't leave a session with uncommitted work.
- Write clean, descriptive commit messages that explain *what* changed and *why*, matching the style of existing history (see `git log`) — e.g. "8 games set registration allowed. Matches played counter corrected." rather than generic messages like "update" or "fix".
- After committing, push to GitHub (`git push`) so work is backed up remotely, not just committed locally.
- Still follow standard git safety practices: review `git status`/`git diff` before committing, never force-push, and never commit files that look like secrets (though note `google-services.json`/`firebase_options.dart` are intentionally tracked here — see Firebase config below).

## Architecture

### Client structure (`lib/`)

- `main.dart` — app entry point and the root auth/routing gate. `AuthTest` (despite the name, this is the real root widget, not a test) listens to `FirebaseAuth.authStateChanges()` and drives the whole top-level flow:
  1. Not signed in → custom-painted Google Sign-In landing screen.
  2. Signed in → `ensureUserDocument()` creates/repairs the Firestore `users/{uid}` doc without ever overwriting fields already set by `CompleteProfileScreen` (only fills genuinely-missing fields; merge writes only).
  3. Streams the user doc; if profile fields (`tennisLevel`, `birthDate`, `city`, `country`) are incomplete → `CompleteProfileScreen`, else → `HomeScreen`.
  - Also owns FCM setup (`setupFCM`/`saveFcmToken`, storing tokens in `users/{uid}.fcmTokens` as a map of token→true so multiple devices are supported) and notification tap routing (`handleNotificationTap` dispatches by `data.type`: `match_reminder`, `match_request`, or default chat/match-accepted → chat screen).
  - Also owns the **presence heartbeat**: `_AuthTestState` mixes in `WidgetsBindingObserver` and writes `users/{uid}.lastActive` (server timestamp, merge write) every 45s while signed in and foregrounded, starting on login/resume and stopping on logout/pause/detached. Other screens derive "online now" from `now - lastActive < 2 minutes` — no separate online/offline boolean or extra listener needed, since it self-expires.
- `screens/` — one file per screen, all fairly large (300–1200 lines) StatefulWidgets that talk directly to `FirebaseFirestore.instance` / `FirebaseAuth.instance` inline (no repository/DAO layer, no state-management framework beyond `provider` for theme). Firestore reads are mostly `StreamBuilder`/`FutureBuilder` wired straight into `build()`.
  - `available_players_screen.dart` — also renders the online-presence dot (green, bottom-right of the avatar) from `lastActive`, and groups/filters players by city.
  - `complete_profile_screen.dart` / `edit_profile_screen.dart` — both save `city` via a display-safe formatter (trim + capitalize first letter only, preserving accents/rest of casing as typed) rather than destroying it. Both also independently render the tennis-level dropdown and availability-day chips through localized strings (`loc.levelBeginner`/etc., a local `_translateDay` helper) — these two screens duplicate this logic rather than sharing it, so a fix/feature added to one (e.g. localization, city formatting) needs to be mirrored in the other by hand.
  - `complete_profile_screen.dart` — also runs the **guest match claim mechanic** (`_claimGuestMatches`, via a `phoneIndex/{phone}/matches` lookup) before the profile write on first login: for each unclaimed guest match matching the new user's phone, it adds them to `players`, sets `guestOpponent.claimedBy`, writes a flipped `claimantResult`, credits their `matchesPlayed`/`wins`/`losses`/`totalDuration` directly (client-side, not via Cloud Function — the only place stats are written outside `applyMatchStats`), and refreshes head-to-head against each claimed match's creator via `H2HService`.
  - `match_history_screen.dart` — for `type: 'guest'` matches, winner/loss perspective (narrative text, trophy, win/loss filter) must be derived by comparing `winnerUid` against `createdBy`, never against the currently-viewing user's UID directly — `winnerUid` is the creator's real UID when the creator won, or `'guest'` when the guest opponent won (that placeholder is set at creation, before the guest has an account, and is never updated afterward). Comparing it to the *viewer's* UID instead of `createdBy` silently flips the result when the claimant views their own history. `player_statistics_screen.dart` has the same `createdBy`-vs-`winnerUid` requirement for its win/loss tally, plus must skip `isTie` matches from the win/loss count entirely (they still count toward `matchesPlayed`). It also tallies `tiebreaksWon`/`tiebreaksLost` while iterating each match's sets, keyed off `setMap['tb1']`/`setMap['tb2']` both being present (win/loss of that tiebreak follows the win/loss of the set it belongs to).
  - **`match_detail_screen.dart` vs `match_details_screen.dart` (singular vs plural) are two separate screens, not a typo.** `match_detail_screen.dart` is opened from `my_matches_screen.dart` and notification taps (`main.dart`) — mostly pending/confirmed matches, though it does also render a completed-match summary. `match_details_screen.dart` is what `match_history_screen.dart` actually opens for completed **regular** matches (guest/doubles have their own `GuestMatchDetailsScreen`/`DoublesMatchDetailsScreen`) — it's the one with the Head-to-Head card and mutual-consent delete flow. A feature meant for "viewing a completed regular match" (e.g. the opponent-rating prompt below) needs to be added to **both**, or it'll silently only show up on one of the two paths users take to reach a completed match.
  - After a **regular** (non-guest, non-doubles) match completes, either participant can submit a one-time opponent rating (1-5 stars, or a no-show flag) via `matches/{matchId}/ratings/{raterUid}`, doc ID pinned to the rater's own UID so it's both self-limiting (one rating per person per match) and rules-enforceable. Ratings are immutable once created (no update/delete). Phase 1 only — guest/doubles opponents aren't real accounts yet, so they're excluded from rating. Implemented in both `match_detail_screen.dart` and `match_details_screen.dart` (see note above on why both), via the shared `widgets/rate_opponent_dialog.dart` (`showRateOpponentDialog()` + `RateOpponentSection` widget) rather than duplicated a third time. Also auto-triggered immediately after submitting a result in `add_match_result_screen.dart` (Uber/InDrive-style, still skippable via Cancel), and reachable by tapping the `rate_opponent` push notification (sent to both players by `notifyPlayersToRate()` in `functions/index.js` when a match completes) — handled in `main.dart`'s `handleNotificationTap`/`openRateOpponentDialog`, which opens the dialog directly rather than navigating to a screen first.
  - `my_profile_screen.dart` — also has the account-deletion "Danger Zone": a type-to-confirm dialog (`_confirmDeleteAccount`, must type the exact localized `deleteAccountConfirmWord` before the destructive button enables) that calls the `deleteMyAccount` Cloud Function (see below) via the `cloud_functions` package. All dialog state (typed text, in-progress spinner, error message) lives in the dialog's own `StatefulBuilder`, not the screen's `State` — a dialog route doesn't rebuild when the screen behind it calls `setState`. On success it signs out locally and closes the dialog; the resulting app-level screen switch (back to the sign-in landing screen, via `main.dart`'s auth listener) is the confirmation shown to the user, so there's deliberately no separate success snackbar to race against the screen tearing down. On failure the dialog stays open with an inline error and the account is untouched, so the user can just retry.
    - **Two gotchas found while testing this that generalize beyond just this screen.** (1) `deleteMyAccount` deletes the caller's `users/{uid}` doc server-side *before* the client's own `signOut()` call resolves, so any live `StreamBuilder<DocumentSnapshot>` on the current user's own doc can briefly observe "document exists but data is null" mid-flow — force-casting `snapshot.data!.data() as Map<String, dynamic>` without a null-guard crashes there (this screen's own listener originally did exactly that; `main.dart`'s top-level listener already guarded against it and was the reference for the fix). Any screen with a live listener on the signed-in user's own doc needs the same `rawData == null` guard, not just an `!snapshot.hasData` check. (2) Signing out from a screen that was reached via `Navigator.push` (rather than a screen `main.dart`'s `AuthTest` renders directly in place) does *not* automatically bring the sign-in landing screen into view — `AuthTest` swaps its own content silently underneath the still-open pushed route(s), invisible until something pops back down to it. The fix here was `Navigator.of(dialogCtx).popUntil((route) => route.isFirst)` right after `signOut()`, rather than a plain `Navigator.pop()` that only closes the dialog. Any future flow that signs the user out from a pushed screen (not just this one) needs the same `popUntil` treatment.
  - `my_profile_screen.dart` / `player_profile_view_screen.dart` — both render an indigo Elo rating badge (`'${loc.eloRatingLabel}: $eloRating'`, `Icons.trending_up`) reading `eloRating`/`eloMatchesPlayed` directly off the user doc, hidden entirely when `eloMatchesPlayed` is 0 so a player who's never finished a regular match doesn't see a meaningless flat starting number. `player_profile_view_screen.dart` places it above the existing reputation badges; `my_profile_screen.dart` places it just under the tennis-level line. Same "read the field, hide if zero" pattern as the Phase 1 reputation badges — no extra Firestore reads. `my_profile_screen.dart` additionally shows a `'#{position} in {city}'` line under the badge once the user has cleared `eloRankingMinMatches`, computed the same way the Ranking screen computes its list (see `ranking_screen.dart` below) so the two can never disagree.
  - `ranking_screen.dart` (Phase 3) — a city-scoped Elo leaderboard, reachable from the home screen. Fetches the same full `users` collection stream `available_players_screen.dart` already uses (no new Firestore query/index — city names aren't stored normalized, so accent/case-insensitive matching has to happen client-side either way) and filters/sorts via `utils/ranking_utils.dart`'s `buildCityRanking()`. Only players sharing the viewer's normalized city **and** with at least `eloRankingMinMatches` (5) rated regular matches appear, sorted by `eloRating` descending — the same minimum the Elo badge's "hidden until qualified" pattern implies, so a lucky first win can't land someone at #1 with almost no evidence behind it. The viewer's own row is highlighted; tapping another row opens `PlayerProfileViewScreen`. A **rating** (Elo, this feature) and a **ranking** (this screen's ordered position) are deliberately different things in this codebase — don't conflate the two when reading `eloRating` elsewhere.
  - `log_guest_match_screen.dart` / `log_doubles_match_screen.dart` — both offer a post-save "share via WhatsApp" dialog (`showDialog` on `navigatorKey.currentContext` so it still works after the logging screen has already been popped back to `HomeScreen`), doubling as an invite channel (`https://tennismatch.app` placeholder link — see the app-link update note below). The two differ in an important way: the singles guest-match share targets one specific opponent phone number (`wa.me/{phone}?text=...`, falling back to the generic composer if no phone was entered) because that phone number is also what the guest-match claim mechanic needs. Doubles matches never collect a phone number for the partner or either opponent at all (plain name fields only) — there's deliberately no claim-into-history mechanic for doubles guests — so `log_doubles_match_screen.dart`'s share always opens the generic `wa.me/?text=...` composer, letting the sender pick a WhatsApp group chat with all three other players at once rather than messaging just one. The message copy also differs accordingly: singles reads as a message addressed to one named opponent, doubles reads as a group announcement.
  - `recent_activity_screen.dart` — city-scoped "recent activity" feed: every completed match from the last `cityActivityWindowDays` (7) played by someone in the viewer's city, newest first, across all three match types. Reduced-detail cards only (who played, who won/tied, how long ago) — deliberately not the full match record (score breakdown, location, notes), even though the underlying documents carry that detail and the broadened read access (see `firestore.rules` note below) would technically allow showing it. Cards are not tappable into the underlying match — this is a display-only feed, not a navigation path into other people's match details. Data comes from two separate Firestore queries (one for `type == 'regular'`, one for `type in ['guest', 'doubles_guest']`) plus a full `users` collection fetch for uid→city lookup, combined and filtered by `utils/city_activity_utils.dart`'s `buildCityActivityFeed()`. Two separate queries, not one, because Firestore's security-rule engine only permits a broad *list* query when it can statically prove every possible result satisfies the rule from the query's own filters — an `OR` across dissimilar match shapes isn't provable that way, so the read rule and the two queries are written to line up filter-for-filter (see below).
- `services/` — small stateless helpers, not a full data layer:
  - `theme_service.dart` — `TennisTheme` (Grand Slam–inspired named color themes, e.g. `fr`/`eng` get bespoke button colors) + `ThemeNotifier` (`ChangeNotifier`, persisted via `shared_preferences`, provided at the app root via `provider`).
  - `h2h_service.dart` — recomputes a user's head-to-head record against one opponent by re-querying all completed matches and writing an aggregate to `users/{uid}/headToHead/{opponentId}`. Called after match completion flows and after the guest-match claim mechanic; it's a full recompute, not an incremental update. Same `winnerUid == 'guest'` placeholder handling as `match_history_screen.dart` applies here — attribute the win via `createdBy`, not a direct UID comparison.
- `widgets/` — small shared presentational widgets (`match_card`, `home_card`, `empty_state`, `error_state`, `set_score_row`, `recent_activity_card` — the Rappi-style home-screen teaser for the recent-activity feed, see below).
  - `recent_activity_card.dart` — wide home-screen banner (not one of the square `HomeCard` grid tiles) showing the single most recent city match this week, tapping through to `recent_activity_screen.dart`. Hidden entirely (`SizedBox.shrink()`) until the viewer's city and all three underlying streams have loaded, rather than showing a loading skeleton — a brief pop-in on first paint was judged less distracting than a placeholder box. Runs the *same* nested-stream + `buildCityActivityFeed()` pipeline as the full screen and just renders `feed.first`; there's no shared "top N" query since the city cross-reference has to happen client-side either way (same reasoning as `ranking_utils.dart`/`buildCityRanking()`).
- `l10n/` (source `.arb` files) and `gen_l10n/` (generated — do not hand-edit, run `flutter gen-l10n`). Supported locales: `en`, `es`. Screens use `AppLocalizations.of(context)!`. Cloud Functions duplicate a parallel set of localized notification strings (`functions/index.js`, the `strings` object) since functions can't import the Dart ARB files — when adding a new user-facing notification string, update both places.
- `utils/day_utils.dart` — day-of-week helpers for availability scheduling.
- `utils/city_utils.dart` — `formatCityDisplay()`, a display-time capitalize-first-letter formatter used everywhere a city name is shown (available players list/header, player profile, my profile). Safe no-op on already-correct values; exists mainly so legacy city values saved before the profile-save fix (lowercase/accent-stripped) still render correctly without requiring every user to re-save their profile. Also `normalizeCityForComparison()`, a comparison-only accent-strip + lowercase helper (never used for display/storage — that destroys casing/accents, which is exactly what `formatCityDisplay()` exists to avoid) shared by `available_players_screen.dart`'s city filter/grouping and `utils/ranking_utils.dart`'s city-scoped ranking, so the accent table only lives in one place.
- `utils/ranking_utils.dart` — `buildCityRanking(allUsers, city)` (Phase 3), a pure filter+sort function: given an already-fetched `users` collection snapshot and a city, returns players sharing that normalized city with `eloMatchesPlayed >= eloRankingMinMatches` (5), sorted by `eloRating` descending. Shared by `ranking_screen.dart` (the full leaderboard) and `my_profile_screen.dart` (the viewer's own position), so the two can never disagree about someone's rank.
- `utils/city_activity_utils.dart` — `buildCityActivityFeed()`, the recent-activity feed's pure filter/normalize function: takes already-fetched regular-match docs, guest/doubles-match docs, and the full `users` collection, and returns a sorted `List<CityActivityMatch>` (one normalized shape covering all three very different underlying match documents — regular/guest use `summary.p1Name`/`p2Name`, doubles has no `summary` at all and instead builds team labels from `team1`/`team2`). `cityActivityWindowDays` (7) lives here too, shared by both the query cutoff and the screen/card. Same "fetch broadly, filter client-side" reasoning as `ranking_utils.dart` — city isn't stored on match documents at all, so cross-referencing via a uid→city map built from the full `users` fetch is unavoidable either way.

### Data model (Firestore, see `firestore.rules` for authoritative shape)

- `users/{uid}` — profile (`name`, `tennisLevel`, `availability`, `birthDate`, `age`, `city`, `country`, `countryCode`, `photoUrl`, `phoneNumber`, `fcmTokens`, `locale`, `uid`, `email`, `createdAt`, `lastActive`) and stats (`matchesPlayed`, `wins`, `losses`, `totalDuration`) as two disjoint field groups — security rules only allow updating one group or the other in a single write, never mixed. Stats fields are written by Cloud Functions (`applyMatchStats`) for normal match completion, **and also directly by the client** in the guest-match claim mechanic (`complete_profile_screen.dart` — the claim isn't a `status` transition, so it can't rely on `applyMatchStats`' triggers, and the security rules do permit the owner to write these fields directly under the same "stats fields" case). `lastActive` is the presence-heartbeat timestamp (see `main.dart` above), grouped with the profile fields. `reputationRatingSum`/`reputationRatingCount`/`noShowCount` (opponent-rating aggregates, see `matches/{id}/ratings` below) and `eloRating`/`eloMatchesPlayed` (Phase 2 dynamic skill rating) are written **only** by Cloud Functions via the Admin SDK (`onOpponentRatingCreated` and `applyEloRatings` respectively) — neither is part of either client-writable field group, so no rules changes were needed for them. `eloRating` defaults to 1200 (Elo starting rating) and `eloMatchesPlayed` to 0 when absent — new users have neither field until their first completed regular match.
  - `users/{uid}/headToHead/{opponentId}` — per-opponent aggregate written by `H2HService`.
- `match_requests/{id}` — `fromUid`/`toUid`/`status` (`pending`→`accepted`|`rejected`|`cancelled`, auto-`expired` after 2 days via scheduled function). Only the recipient can accept/reject; only the sender can cancel.
- `phoneIndex/{phone}/matches/{matchId}` — lookup index keyed by phone number, used so a newly-registered user can find unclaimed guest matches logged against their number without needing broader query permissions on `matches`.
- `matches/{id}` — the central document, shape varies by `type`:
  - Regular 1v1: `players: [uid1, uid2]`, `player1Uid`/`player2Uid`, `status` (`pending`→`confirmed`→`completed`, or `cancelled`). Historically had **no `type` field at all** (every read site across the client and Cloud Functions treats a missing `type` as `'regular'`, e.g. `data['type'] as String? ?? 'regular'`). As of the recent-activity feed, `add_match_result_screen.dart` now explicitly writes `type: 'regular'` in the same batch that transitions the match to `completed` — purely additive (every existing read site already treats it as equivalent to the old missing-field state), done so the feed's Firestore query/security-rule pair can target completed regular matches by an exact-match filter rather than an unprovable "field absent" condition. Matches completed **before** this change still have no `type` field and are excluded from the feed (acceptable, since the feed only ever shows the last 7 days), but remain fully functional everywhere else (detail screens, history, stats, deletion) since those all already handle the missing-field case.
  - `type: 'guest'`: single registered player (`players.size() == 1`) logging a match against an unregistered opponent (`guestOpponent`, matched by phone number); can later be "claimed" by the guest if they sign up (rules allow updating `guestOpponent`/`players`/`claimantResult` while `guestOpponent.claimedBy == null`). `winnerUid` is the creator's real UID if they won, or the literal string `'guest'` if the (then-unregistered) opponent won — see the `match_history_screen.dart`/`h2h_service.dart` notes above for why this matters.
  - `type: 'doubles_guest'`: only the creator (`createdBy`) is a real account; partner/opponents are name strings, not UIDs.
  - `messages/{id}` subcollection — per-match chat; `activeChatUsers` map on the parent match suppresses push notifications while a user has the chat screen open; `deletionRequest` implements a mutual-consent delete flow (either participant proposes, both must have `seenBy` it, then the requester can delete once `status == 'accepted'`).
  - `ratings/{raterUid}` subcollection — Phase 1 opponent ratings, regular matches only (see `match_detail_screen.dart` above). Doc ID is the rater's UID; fields are `ratedUid`, `stars` (0-5, 0 when `noShow`), `noShow`, `createdAt`. Client can create, never update/delete.
- Firestore composite indexes (`firestore.indexes.json`) are hand-maintained alongside the queries that need them — if you add a new compound `where`/`orderBy` query, add the matching index here.
- **Regular matches are participant-only readable, except completed ones (recent-activity feed).** The base `matches/{matchId}` read rule is still `isParticipant(resource.data.players)` for anything pending/confirmed (scheduling details, chat, etc. stay private to the two players). Guest and `doubles_guest` matches have always been broadly readable by any authenticated user (the Dart code filters by phone/`claimedBy` client-side). A new rule branch, added for the recent-activity feed, additionally allows any authenticated user to read a regular match once `type == 'regular' && status == 'completed'` — i.e. only after it's done, never while pending/confirmed. This is a deliberate, scoped privacy trade-off (previously a regular match's result was visible only to the two participants; now anyone in the app can technically read the full completed document, including score/location/notes, even though the recent-activity feed itself only ever renders a reduced summary). The corresponding `confirmed`→`completed` update rule's `affectedKeys().hasOnly([...])` allowlist had to add `'type'` (since `add_match_result_screen.dart` now writes it in that same update), and the mutual-consent delete rule had to add an explicit `resource.data.type == 'regular'` branch alongside its old `!('type' in resource.data)` check, or newly-completed regular matches would become permanently undeletable.
- **List queries and security rules: the query's filters must textually match the rule, not just be logically implied by it.** Firestore evaluates `list`/collection queries against their *potential* result set using the rule's literal structure — it can't reason about data invariants (e.g. that `completedAt` being set implies `status == 'completed'`), so a query has to explicitly filter on every field the rule's matching branch checks, with the same operators, or the whole query is rejected with `permission-denied` (not silently filtered per-document). This is why the recent-activity feed's regular-match query filters on `type`, `status`, *and* `completedAt` even though `completedAt` alone would already be practically sufficient — and why it's a *separate* query from the guest/doubles one rather than one unified query, since the two match shapes need genuinely different rule branches to prove against (`type in ['guest','doubles_guest']` is directly provable against Firestore's `whereIn`, but that branch doesn't cover regular matches and vice versa).
- **`firestore.rules` can drift from what's actually live.** Rules have been hand-edited directly in the Firebase console at times, bypassing this file — before editing `firestore.rules` locally, diff it against the console's current rules (Firestore → Rules tab) rather than assuming the repo copy is authoritative, or a local edit + deploy can silently roll back console-only changes. Always deploy with `firebase deploy --only firestore:rules` after editing so the two stay in sync going forward.

### Cloud Functions (`functions/index.js`)

Single-file Node.js Cloud Functions v2 codebase. Mostly Firestore-triggered or scheduled, plus one callable (`deleteMyAccount`, see below) — no plain HTTP endpoints:

1. `onNewChatMessage` — push to the other match participant, suppressed if they're actively viewing the chat (`activeChatUsers`).
2. `onMatchRequestReceived` / `onMatchRequestAccepted` — push notifications on request lifecycle, localized via the recipient's stored `locale`.
3. `onMatchScheduleReminder` — runs every 30 min, pushes 24h and 1h reminders for `confirmed` matches with a `scheduledDate` in range.
4. `onMatchRequestExpiry` — runs daily, expires `pending` requests older than 2 days.
5. `onMatchCreatedCompleted` / `onMatchUpdatedCompleted` + shared `applyMatchStats()` — the *only* place stats fields (`matchesPlayed`/`wins`/`losses`/`totalDuration`) are written, symmetrically for both players, using the Admin SDK to bypass client security rules. Handles `regular`/`guest` (via `players` array + `winnerUid`) and `doubles_guest` (via `createdBy` + `winnerTeam`) differently. `onMatchUpdatedCompleted` also calls `notifyPlayersToRate(matchId, match)` right after `applyMatchStats()`, pushing a `rate_opponent` notification (`data: {type: 'rate_opponent', matchId}`) to both players so the one who didn't submit the result still gets a path into the rating dialog (see below).
6. `onOpponentRatingCreated` — triggers on `matches/{matchId}/ratings/{raterUid}` creation; rolls the rating up onto the rated player's profile (`reputationRatingSum`/`reputationRatingCount` for a star rating, `noShowCount` separately for a no-show report — never both from the same rating, so a no-show never drags down the star average).
7. `applyEloRatings(match)` — Phase 2 dynamic skill rating, called from both `onMatchCreatedCompleted` and `onMatchUpdatedCompleted` right after `applyMatchStats()` (a no-op for anything that isn't a regular 1v1 match, so it's harmless being called from the guest/doubles path too). Standard Elo formula (`expected = 1 / (1 + 10^((opponentRating - rating)/400))`), starting rating 1200, K-factor 32 for a player's first 20 rated matches then 16 once established (`eloKFactor()`), score 1/0/0.5 for win/loss/tie. Runs inside a Firestore transaction reading and writing both players' `eloRating`/`eloMatchesPlayed` together, so two matches completing for the same player around the same time can't read a stale rating. Excluded from `guest` (opponent isn't a full account) and `doubles_guest` (outcome depends on a partner's skill too) — only regular matches with exactly two real UIDs in `players` feed it.

**Backfilling existing users:** `functions/scripts/backfillElo.js` is a one-off, non-deployed Node script (not exported from `index.js`, so `firebase deploy` never touches it) that replays every historical completed regular match in chronological order (`completedAt` ascending) using the identical formula/K-factor as `applyEloRatings()`, so existing testers' first-ever ratings reflect their actual match history instead of starting flat at 1200. Needs a downloaded service account key (`functions/serviceAccountKey.json`, gitignored — never commit it) and is run manually once via `npm run backfill-elo` from `functions/`. Safe to re-run — it always recomputes from scratch rather than compounding. If the live `applyEloRatings()` formula/constants ever change, this script's copy needs to be updated to match or a re-backfill will disagree with it.

8. `deleteMyAccount` — the app's one callable function (`onCall`, invoked from the client via the `cloud_functions` package, `my_profile_screen.dart`'s Danger Zone), rather than a Firebase Auth `onDelete` trigger — auth `onDelete` triggers have documented reliability gaps (they don't fire for batch deletions and behave inconsistently for some SDK-initiated deletes), so a callable function is used instead to keep this one atomic, authoritative flow. Order matters: all Firestore/Storage cleanup runs *before* the Firebase Auth account is deleted, never after — if a cleanup step throws, the user's account still exists and they can just retry, rather than being locked out with half-deleted data. Cleanup scope: cancels every `match_requests` doc in either direction (`fromUid`/`toUid`) involving the caller — both Incoming and Outgoing Requests screens do a *live* profile lookup of the other participant, unlike `matches`, so a stale pending request pointing at a deleted profile would otherwise break that screen for the other person; recursively deletes (`db.recursiveDelete()`) every `guest`/`doubles_guest` match the caller created (plus its `phoneIndex` lookup entry), which is safe because those match types only ever have one real registered account on them until claimed, so it can never remove data another still-active user depends on — **regular matches, and guest matches the caller merely claimed (created by someone else), are deliberately left untouched**, matching the same "matches/stats already belong to the other player" reasoning used throughout this codebase; deletes the Storage profile photo; recursively deletes the caller's own `users/{uid}` doc (including its `headToHead` subcollection). Only then does it call `admin.auth().deleteUser(uid)` — the Admin SDK isn't subject to Firebase's client-side "requires recent login" restriction, so the Flutter client never needs to re-trigger Google Sign-In before calling this, unlike the equivalent self-service `currentUser.delete()` would require.

All user-facing notification copy is duplicated per-locale in the `strings` object at the top of the file — follow that pattern (add a key to both `en` and `es`) rather than inlining new literal strings.
